Saving Look Inside the Book

Archive note: Amazon.com, Mar 2007 – Apr 2008 (from resume timeline). Role: [TODO: confirm team/role title — resume lists Senior Software Development Engineer, Scaled Cloud Services]

I joined Amazon because I was excited about the Kindle: its form factor, its e-paper display, and a Freescale processor I already knew. An always-connected device that needed only occasional recharging was a compelling option for ubiquitous computing.

Then an urgent problem landed. The book page images behind "Look Inside the Book" lived on neglected machines with expiring leases, and the developers and team who built the system were long gone. I enjoy a challenge, and I had never shipped a large-scale network service into production, so I took it on. I dug in, figured out how the system worked, and documented it.

It was bad. The fleet of over 50 machines was very old, and the secondary copies of the page images were long gone. Every few weeks another machine died, and its page images went with it. There was no easy way to recreate them: we scan physical books two pages at a time. The scanning is automated, but still costly. [TODO: scale — how many page images / books / TB? Resume figures vary: 80 TB migrated, 220 million images served, 500 million unique pages]

I made a plan. Step one: archive the surviving page images into AWS S3. My scripts drove dozens of machines pushing images in parallel, verifying each image and tracking the inventory. The machines were old and flaky and would lock up or reboot; the scripts restarted, found the last archived page, and carried on.

While that ran, the S3 team contacted me urgently: "What the #### are you doing, and how fast can you slow it down? You are using up S3 drive space faster than we can add new machines." I added throttles and worked closely with the AWS team to coordinate the scale. They understood the urgency: any day, another machine could die and take tens of thousands of book page images with it.

Of course, one did. It crashed, rebooted, and on reboot immediately formatted all its disks. I had little deep experience with Linux hardware internals then, and I learned something I would not have imagined existed: a BIOS setting that wiped the disks on reboot. I verified the setting was off on every remaining machine. The surprise was that none had wiped in all the years before; I assume the setting got switched on later in the machine's life.

With throttled replication running smoothly, I had time to design a replacement page-image service and learn the tools and technology to build it. Defining the spec and designing the architecture was fun, and it was not common in the consumer-focused ubiquitous computing products I had built.

Along the way I jumped into several emergencies on unrelated services: an Oracle server that crashed with a memory dump on Christmas Eve, and a worker script that started deleting an internal video file archive. Each one taught me the value of systems that diagnose and repair themselves and report and alert effectively. So I set a high bar for diagnostic code and dashboards in the new service. It ended up about 20% functional code and 80% diagnostic code: code that detected failure modes, attempted recovery, logged events, triggered hard alerting, performed automatic resets, and handled general logging. I was not aiming for a ratio; I only noticed it later.

The result: the service worked. It was reliable and cheap, built entirely on AWS (S3 and EC2), and it is still in use more than ten years later.

Still running (October 2026)

Amazon's "Read sample" viewer is now Kindle for Web (read.amazon.com/sample), but a print book's sample still loads page images named the way I designed them, for example 0785238921.01.S001.JUMBOXXX.jpg: the ISBN, .01, a base-36 page code (S001), and the JUMBOXXX size. Today they come through CloudFront signed URLs, a layer added later; CloudFront launched in November 2008, after my time on the service.
